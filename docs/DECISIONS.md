# 설계 결정 기록

PRD v0.2를 구현하면서 정한 것, PRD와 달라진 것, 그 이유를 기록한다. 결정을 바꿀 때는 기존 항목을 지우지 않고 새 항목을 추가한 뒤 이전 항목에 `대체됨: Dxx`를 적는다.

검토 근거: PRD 자체 검토와 외부 리뷰(GPT) 내용을 함께 반영했다. 리뷰에서 나온 항목은 `(리뷰)`로 표시한다.

---

## D0. 데이터 소스와 가상 데이터 (2026-10-16)

- **결정**: 가상 시나리오 데이터로 데모하거나 평가하지 않는다. 섀도 테스트를 할 것이므로 서사는 실제 커뮤니티 데이터에서만 얻는다.
- **수집 권한 확인 결과**: [DATA_POLICY.md](DATA_POLICY.md)의 "확인 결과" 참고. 디시 약관은 자동 수집을 명시적으로 금지하고, 네이버 종목토론 공식 API는 증권사 대상이다.
- **결정**: 프로젝트 소유자가 위험을 인지한 상태에서 수집을 진행하되, DATA_POLICY.md의 안전장치를 지킨다. 병행해서 두 회사에 데이터 이용 문의를 보낸다([outreach/](outreach/)).
- **예외**: 규칙 단위 테스트(예: 같은 글 10건 복제 → 독립 근거 1건)는 사람이 직접 쓴 최소 픽스처를 쓴다. 이 픽스처는 서사가 아니라 코드 검증용이다.

## D1. 수집 안전장치

- 읽기 전용. 글쓰기·추천·로그인 기능을 만들지 않는다.
- 소스별 요청 간격 3초 이상, 동시 요청 1개. 목록 폴링은 1–2분 간격.
- 차단·캡차·로그인 요구·4xx 반복을 감지하면 해당 소스를 `blocked`로 바꾸고 멈춘다. 프록시 회전이나 캡차 풀이 같은 우회는 하지 않는다. 해제는 사람이 한다.
- 작성자 ID·닉네임·IP는 저장하지 않고 `author_hash = HMAC(salt, source + 작성자)`만 저장한다.
- 원문은 로컬 DB에만 둔다. 공개 저장소에는 실제 게시글을 커밋하지 않는다(`data/`는 gitignore).

## D2. 섀도 테스트를 위한 시간 정합성 (PRD 10.3, 15.4)

- 포워드 수집이 최우선이다. 실시간으로 모은 데이터만 `available_at`이 실제 시각이고, 지나간 날은 나중에 다시 만들 수 없다. 그래서 수집기를 UI보다 먼저 상시 가동한다(ROADMAP M3).
- 댓글·조회 수는 문서 행에 두지 않고 `document_metric_snapshots`에 관측 시각과 함께 쌓는다. 새 글은 +10분, +1시간, +6시간, +24시간에 다시 읽는다. 신호는 "그 시점에 보였던 값"만 쓴다.
- 백필(과거 글 소급 수집)은 `retrospective` 모드로만 처리한다. 백필 시점의 댓글·조회 수는 미래 정보이므로 신호에 쓰지 않고, 삭제된 글이 빠져 있다는 점(생존 편향)을 명시한다. 백필 결과와 포워드 성과는 섞지 않는다.
- 코드에서 `datetime.now()`를 직접 부르지 않고 `Clock`을 주입한다.

## D3. 저장소

- SQLite(WAL) 하나만 쓴다. PRD 17장의 DuckDB는 분석 수요가 생길 때 추가한다.
- `graph_events`, `wiki_revisions`, `edge_evidence`, `classification_runs`, `document_metric_snapshots`는 추가만 하고 수정하지 않는다.
- `nodes`, `edges`의 상태 컬럼은 "현재 상태" 캐시이고, 과거 상태는 `graph_events`로 복원한다.
- 모든 시각은 시간대가 있는 UTC로 저장한다. 시간대가 없는 값은 저장 단계에서 거부한다.

## D4. 개체·토픽 정규화 (PRD 7.4 변경)

- 순서: canonical key → alias 사전(은어 포함) → 문자열 정규화와 퍼지 매칭으로 후보 → LLM이 후보 중 선택하거나 신규 제안 → 앱이 검증한 뒤 후보 상태로 등록.
- PRD 7.4의 3단계(임베딩 유사도)는 후속으로 미룬다. 초기 볼륨에서는 alias와 퍼지 매칭으로 충분한지 먼저 측정한다.
- 토픽은 기업과 달리 티커가 없어서 중복이 쉽게 생긴다("HBM" vs "HBM Supply"). LLM에게 항상 기존 토픽 목록을 보여주고 거기서 고르게 한다.

## D5. 내러티브 단위 (PRD 7.2 변경, 리뷰)

- **Claim**: 문서 하나에서 추출한 주장. 주어, 술어, 대상, 극성(성장 근거 / 제약 요인 / 중립), 입장.
- **Narrative**: 같은 명제를 말하는 claim 묶음. 핵심 명제, 관련 노드, 지지 claim, 반대 claim, 상태(`emerging / spreading / contested / reversed / fading / split`)를 가진다.
- 그래프에는 claim을 노드로 그리지 않는다(수천 개가 된다). 대신 narrative 노드를 둔다. PRD 7.2의 `claim` 노드 유형을 `narrative`로 바꾼다.
- 상태 판정은 시간 창별 claim 수와 지지·반대 비율 변화로 하는 규칙 기반이다.

## D6. 확산 축과 검증 축 분리 (리뷰)

- 문서마다 `derivation_group`(복사·전재 묶음)을 둔다.
- 확산 지표는 복제를 포함한 문서 수·소스 수·작성자 수다. 독립 근거는 서로 다른 derivation group이면서 서로 다른 작성자인 것만 센다.
- 엣지는 두 단계다. 발견 후보(근거 1건, 점선, "처음 관측됨")와 관측 확정(독립 근거 2건 이상, 실선). 노출 문턱과 확정 문턱을 따로 둔다.
- "관측 확정"은 그 관계가 반복해서 이야기된다는 뜻이지 주장 내용이 사실이라는 뜻이 아니다. 주장의 사실 여부는 별도의 검증 상태(기본값 `커뮤니티 주장 · 미검증`)로 표시한다.

## D7. 변화 원인 구분 (리뷰)

- `graph_events.cause`: `observed_new`(새로 관측) / `backfill`(과거 자료를 늦게 수집) / `reprocess`(모델·프롬프트·스키마 변경으로 재분류) / `source_added` / `user_action`.
- 모든 처리는 `pipeline_runs`에 속하고, 실행마다 mode(`live` / `retrospective`)와 model·prompt·schema 버전을 기록한다.
- 시간 재생 기본값은 "당시 시스템이 알던 상태"다. 사후 재구성은 별도 계보로 두고 화면에 `재구성 모드`를 표시한다.

## D8. 탐색 깊이 계산 (PRD 8.2 보완)

- 시점 t에 관측 확정 상태인 의미 관계 엣지만으로 root에서의 최단거리를 잰다. `CO_MENTIONED_WITH`는 거리 계산에서 뺀다(넣으면 거의 모든 노드가 Depth 1이 된다).
- depth > `max_depth`인 노드는 개인 그래프에서 숨기고 글로벌 그래프에는 남긴다.

## D9. 강도·활성도·휴면 (PRD 11장 보완)

- 엣지 강도(t) = Σ(독립 근거) exp(−(t − available_at) / τ), τ = 7일(설정값).
- 노드 활성도 = 6시간 버킷 언급 수의 감쇠 합. 수집량 대비 비중도 같이 저장한다.
- 이벤트는 상태가 바뀔 때만 기록한다: `NODE_CREATED`, `NODE_DORMANT`(활성도가 기준 아래로 72시간), `NODE_REACTIVATED`, `EDGE_CREATED`, `EDGE_CONFIRMED`, `EDGE_WEAKENED`, `EDGE_TYPE_CHANGED`, `NARRATIVE_STATE_CHANGED`.
- 크기·두께 같은 연속 값은 이벤트가 아니라 버킷 시계열에서 계산한다.

## D10. 관심도 정규화와 관측 공백 (리뷰)

- 언급량은 절대 건수와 수집량 대비 비중을 함께 저장하고, 신호는 비중으로 판단한다.
- `source_health`에 수집 성공·실패와 수집량을 시간대별로 남긴다. 공백 구간은 타임라인에 표시하고, 그 구간의 하락은 신호에서 뺀다.
- 화면 문구는 "시장 전체"가 아니라 "선택한 커뮤니티에서 관측된 내러티브"로 쓴다.

## D11. 첫 화면은 "달라진 점" (리뷰)

- 지난 방문 이후(또는 고른 두 시점 사이) 새로 관측된 것 / 달라진 기존 이야기 / 그 근거를 먼저 보여준다.
- 항목마다 원인 배지(D7)와 근거 수(확산 vs 독립, D6)를 붙인다. 항목을 누르면 그래프의 해당 부분이 강조되고 위키의 해당 섹션이 열린다.
- 판정은 이벤트와 내러티브 상태 변화에 대한 규칙 기반 diff다. 새 대시보드를 만들지 않고 그래프 옆 패널 하나로 둔다.

## D12. LLM 사용과 비용

- 분류 모델은 `claude-haiku-5-5`. 가격(2026-10 기준): 입력 $0.10, 출력 $0.50 / 100만 토큰(프롬프트 10만 토큰 이하), Batch API 50% 할인. 예산을 잡기 전에 공식 가격을 다시 확인한다.
- Haiku 5.5는 thinking이 기본으로 켜져 있으므로 `effort: low`로 쓰고 `max_tokens`는 thinking을 포함해 여유 있게 잡는다. `temperature`는 지정할 수 없으므로 구조화 출력(`messages.parse()` + Pydantic)으로 형식을 강제한다.
- 모든 LLM 출력은 바로 반영하지 않고 "변경안(ChangeSet)"으로 받아 앱이 검증한 뒤 반영한다(PRD 4.1).
- 프리필터: 현재 개인 그래프 노드의 alias에 걸리는 글은 전부, 나머지는 표본만 LLM에 보낸다.
- 테스터는 미리 계산된 결과를 조회만 하고 LLM을 호출하지 않는다.

## D13. 평가 방법 (가상 정답 대신)

- **골드셋**: 실제 글 약 300건을 시간대별로 층화 추출해 LLM이 먼저 라벨을 달고 사람이 검수한다. 개체·토픽·주장 추출의 정밀도와 재현율을 잰다. 골드셋은 로컬에만 둔다.
- **사건 기준 점검**: 실적 발표일, SEC 공시 시각처럼 공식 시각이 있는 실제 사건 목록을 두고, 관련 서사가 언제 관측됐는지 잰다. 예측이 아니라 탐지 지연을 측정한다.

## D14. 기타

- 문서 버전은 v0.2로 통일한다(PRD 21장의 "V0.1" 표기는 오기로 본다).
- 그래프 레이아웃은 전체 기간의 합집합 그래프에 고정 시드로 한 번 계산해 좌표를 고정하고, 재생 중에는 보이기·숨기기만 한다(PRD 11.4).
- 이슈 군집 형성·분화 탐지는 P1로 미룬다.
- 저장소 이름은 `Narratvie-Radar`(철자 그대로)이고 제품 이름은 Narrative Radar다.
